Why AEGIS

Built for teams that answer for what the agent did

If you ship changes for clients, or work where every change needs a named approver and a record, "the agent opened a PR" isn't enough. AEGIS is built around four properties.

Self-hosted

Server, workers, Redis, repo clones and the Docker sandbox run on infrastructure you control. Docker Compose, Kubernetes and Render manifests are included, and the code is MIT-licensed — read it, fork it, audit it.

docker-compose.yml · k8s/ · render.yaml

Multi-tenant

One deployment, many clients. Each tenant gets its own API keys, roles, OIDC SSO, quota, repo, retention policy and audit chain. Git tokens and bring-your-own model keys are encrypted at rest.

engine/tenant*.js · rbac.js · sso.js

Approval-gated

In approval mode every patch is held in a review queue before it touches the worktree. A webhook alerts your reviewers, and anyone with the member role or above resolves it — approve, retry, skip or escalate, with a note. Approve applies the exact patch the reviewer saw. Any single step can also demand sign-off.

engine/approval-gate.js

Audit-logged

Submits, cancels, review decisions, key, user, SSO and retention changes, and merges to your base branch are recorded with who, role and IP. Events form a per-tenant hash chain, each HMAC-signed, exportable as JSON or CSV with a chain-verification result.

engine/audit-log.js

Who it's for

Agencies and consultancies

Give every client its own tenant: their repo, their keys, their quota, their retention rules — and an exportable audit trail to hand over when the engagement ends.

Regulated teams

Keep code, state and test execution on your own infrastructure, put a person between the model and the branch, and give auditors a log they can verify instead of a screenshot.

Trust

What stays on your infrastructure — and what doesn't

Self-hosted doesn't mean air-gapped. Here is where each piece of data lives.

Source code, clones, worktreesYour repo volume. Disconnecting a tenant's repo removes the clone (DELETE /tenants/:id/repo).
Plans, patches, test output, traces, review recordsYour Redis, on a retention clock you set per tenant (1–365 days after a workflow finishes).
Lint and testsYour Docker sandbox, with no network inside it. If Docker is missing, the step fails by default rather than running on the host.
Prompts to the modelAnthropic's API, using your key — or the tenant's own key on plans that allow it. Anthropic's retention terms apply; AEGIS's zero-retention mode doesn't change them.
Memory embeddings (optional)OpenAI, only if you set OPENAI_API_KEY. Never used for zero-retention tenants.
Usage and billingCounts only (runs, steps, tokens, minutes) in your Postgres. Stripe is involved only if you turn billing on.

Limits, stated plainly

  • Not SOC 2 certified. The control map and roadmap are public; status is on the security page.
  • SSO is OpenID Connect (Okta, Entra ID, Google Workspace, Auth0, Keycloak). SAML needs an OIDC bridge.
  • Approval mode is a deployment-wide setting today, not a per-tenant policy. A step can add the gate for itself but can never waive it.
  • The audit log can't be pruned — that is what makes it tamper-evident. Zero-retention tenants get task text redacted before it is hashed.

What it actually is

A REST API plus a worker pool — not a library

AEGIS is a Node.js (ESM, Node 20+) service: server.js accepts tasks, a BullMQ worker pool executes them. You run it, you don't import it.

7
specialized agents — feature-builder, debugger, refactorer, test-writer, security-editor, review-guard, meta-reviewer
1
worktree and branch per workflow, with git-revert step rewind and a full audit trail
N
tenants — isolated API keys, quotas, and queues, running concurrently under Redis-backed locks
Capabilities

What's actually implemented

No roadmap items on this list — every one of these ships in v2.0.0.

DAG-based planning

The planner LLM returns steps with depends_on; forward references are rejected and cycles are caught with Kahn's algorithm before anything runs.

Docker sandbox

Every lint and test run happens in a container. If Docker isn't available, the step hard-fails — no silent unsandboxed execution.

Git-based rollback

Each workflow gets its own worktree. Steps commit or roll back individually; a specific step can be rewound with dependents reset.

Multi-tenancy

Per-tenant API keys, roles, OIDC SSO, quotas, retention, and isolated worktrees and queues — concurrent workflows never step on each other.

Approval gate

Set CLAUDE_AUTONOMY=false to hold every patch in the review queue, or flag individual steps with requiresApproval. Alerts by webhook; every decision is audit-logged.

Vector memory

Hybrid cosine + BM25 + recency search over prior fixes, with per-tenant adaptive weighting. Degrades to a no-op without an embeddings key.

Dead letter queue

Exponential backoff retries, staleness sweeps, and webhook alerts once a step exceeds DLQ_MAX_RETRIES.

PR automation

Opens a pull or merge request after a workflow merges — GitHub, GitLab, or Bitbucket — targeting your configured branch.

Architecture

Every step is validated, sandboxed, and reversible

Agent inputs include AST-level repo context from repo-scanner.js and prior-fix context from vector-memory.js. Failures don't retry silently — they escalate through the DLQ.

architecture.txt
POST /task ──▶ orchestrator.js (runSystem)
                 │
                 ├─ planner LLM call → JSON plan → DAG validation
                 │   (cycle detection, dependency checks, agent-name checks)
                 │
                 └─ BullMQ queue ──▶ workers/agent-worker.js
                                       │
                                       ├─ agent-runner.js: feature-builder |
                                       │   debugger | refactorer | test-writer |
                                       │   security-editor | review-guard |
                                       │   meta-reviewer
                                       │
                                       ├─ review-system.js: structural patch
                                       │   validation, pre-flight checks
                                       │
                                       ├─ sandbox.js: Docker-isolated
                                       │   lint + test run
                                       │
                                       ├─ git.js: per-tenant/per-workflow
                                       │   worktree, commit, or rollback
                                       │
                                       └─ approval-gate.js: hold for human
                                           review if CLAUDE_AUTONOMY=false

Failures ──▶ workers/dlq-worker.js: retry with backoff, escalate to
             review queue after DLQ_MAX_RETRIES, staleness alerts

Quickstart

Running in four commands

Redis Stack is required, not plain Redis — only FT.SEARCH gives the server and worker a shared vector index.

1
Clone and configure. Fill in ANTHROPIC_API_KEY at minimum.
2
Start Redis Stack. Plain Redis won't share the vector index across processes.
3
Run the server and workers. API server, agent worker, and DLQ worker are separate processes.
4
Submit a task. Poll the workflow until it reaches a terminal state.
terminal
# 1–2. clone, configure, start Redis Stack
git clone https://github.com/Naveenub/aegis.git
cd aegis && npm install
cp .env.example .env
docker run -d -p 6379:6379 redis/redis-stack-server:latest

# 3. server + workers (separate processes)
npm run server
npm run worker
npm run dlq-worker

# 4. submit a task
curl -X POST localhost:3000/task \
  -H "Authorization: Bearer $AEGIS_API_KEY_DEFAULT" \
  -d '{"task": "add input validation to login"}'
